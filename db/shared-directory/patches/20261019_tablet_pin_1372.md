# Tablet PIN Directory rollout

Apply the SQL patch and its verification only to the canonical Directory database with the privileged migrator. It stores bcrypt PIN hashes and registered-device state exclusively in the authority; it neither changes `cerp_terminal_pins` nor grants site runtime access to PIN material.

The authority generates a neutral device UUID and a one-use, 15-minute pairing code. Pairing returns a 256-bit device secret. The unified Android APK encrypts that credential with Android Keystore; its native bridge accepts only the exact CERP HTTPS origin and the main frame. The implementation has emulator instrumentation coverage. Physical-tablet acceptance remains outstanding; this is not hardware attestation.

## Invalidation and authentication

- Each employee chooses a four-digit PIN after signing in with a password. The PIN is stored as a bcrypt hash in the authority.
- A tablet is scoped to the verified server caller's database. Its hardware record does not assign employee roles or modules.
- Changing or revoking a PIN invalidates that employee's PIN sessions and MFA challenges, while preserving password sessions. Revocation retains a monotonic version tombstone so recreating the same PIN cannot revive an old session.
- Renewing pairing invalidates previous device sessions, challenges and secrets. Revocation is final for that inventory record; registering the tablet again creates a new record.
- Administrators retain MFA after a valid PIN. Five failed PIN attempts block the account/device pair for 15 minutes. Attempts during a block do not extend it, and the password limiter remains separate.
- PIN/device management and accepted PIN authentication are audited without recording the PIN, pairing code or device secret. The login audit runs after the separate MFA transaction, preventing its user foreign-key lock from blocking MFA.

## Deployment and verification

Apply the additive patch, including the authority runtime's challenge-update grant, before activating the new Directory runtime. Deploy Directory before the site APIs, then the clients. Ordinary password identities omit tablet-specific fields for compatibility with the previous site API during rollout. Keep the new Directory validation when rolling back a site API after PIN sessions or challenges have been issued.

`scripts/managed-tests/check-tablet-pin-http-1372.cjs` runs signed HTTP calls against an owned disposable PostgreSQL fixture using the real `cerp_directory_app` role. It checks shared-device users, administrator PIN/MFA, version and challenge invalidation, pairing renewal/revocation, cross-site isolation, throttling, password compatibility and secret-free durable audits. Supply its database port through `CERP_TABLET_PIN_FIXTURE_PORT` and the disposable database credential through `CERP_TABLET_PIN_FIXTURE_PASSWORD`; the script does not contain that credential. It must never target a deployed Production or Test database.

The public HTTP contract suite also checks camelCase input, validation before upstream calls, 204 mutations, and the closed mapping of expected Directory errors. Unexpected upstream details remain private.

## PIN-only lookup (TABLET-PIN-ONLY-20261021)

After `20261021_tablet_pin_only_1403.sql`, the normal tablet login may omit the
username. The Directory checks the paired device secret first, then resolves a
unique HMAC lookup of the four-digit PIN and finally verifies a distinct
domain-separated HMAC derivation with bcrypt. The PIN, the lookup and the
bcrypt input are never returned, audited or logged. A PIN is therefore a
workshop credential on an approved tablet, not a replacement for password MFA:
an administrator still receives the normal MFA challenge.

Existing PIN rows have no lookup and return `pinOnlyReady: false` until the
employee signs in normally and saves the PIN again. The optional `username`
field exists only to keep older client payloads compatible: it is compared
against the account resolved by the lookup and is never a fallback
authentication path. The new unique partial index makes a collision an atomic
neutral `409` response. PIN choices, including collisions, are limited per
authenticated profile; login failures are limited by the existing IP and
device scopes (100 attempts per IP and five per approved tablet in 15 minutes).

`AUTH_RATE_LIMIT_HASH_KEY` is also the server-only key for the two
domain-separated derivations. During a supervised key rotation, first deploy
the new key and runtime, invalidate existing tablet PIN sessions/challenges,
then have every tablet-PIN user sign in with their password and save a new PIN.
The stored non-secret key fingerprint makes status return `pinOnlyReady: false`
after rotation. A v2 verifier derived with the retired key cannot be checked
after rotation; password reauthentication and PIN reconfiguration is required.
Do not drop the additive columns as a rollback shortcut.

The pre-PIN-only backend cannot verify the version-2 bcrypt(HMAC) value and
its setter does not preserve the new lookup fields. A software rollback must
therefore use a qualified fallback which retains PIN-v2 support. If that is not
available, disable tablet PIN login and use password/MFA; never mass-reset or
drop PIN-only state to make an older runtime start.
