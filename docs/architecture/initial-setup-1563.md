# Test signup and initial ERP setup — #1563

Frontend issue: https://github.com/BigFootLime/crp-systems-web/issues/1563. Project Office code: `ERP-ONBOARDING-20261014`. Feature branch: `feature/1563-initial-setup` in both repositories. Functional guide and design evidence are in the matching frontend `docs/architecture/initial-setup-1563.md`.

Public routes `GET/POST /auth/test-registration` require the actual pool database `cerp_test` and an explicit `CERP_TEST_REGISTRATION_ENABLED=true` opt-in. Production remains closed even with a spoofed Test header or an incorrectly enabled flag. The client cannot assign a role. Newly created accounts receive the existing administrator primary role, `is_superadmin=true` and `mfa_reenrollment_required=true`; existing accounts are never changed. Password hashing, TOTP encryption, challenge lifecycle, durable rate limiting, MFA assurance and recovery codes use the existing authentication implementation.

Canonical RH contracts hold the weekly and daily targets. Schedules use the existing day convention (Sunday=0). No HR address, identity number, birthday, salary or phone is fabricated. The generated `TEST-<user id>` is only an internal employee identifier. Signup idempotence uses a keyed request digest, never a stored plaintext password. Audit is transactional and minimizes personal data.

Authenticated `/admin/onboarding/{status,progress,company}` routes require a database-backed superadministrator check. Status reads canonical data, not a list of frontend acknowledgements. Company edits use optimistic concurrency and idempotence. Legal versions preserve unexposed fields and cannot be backdated over an existing version. The readiness checklist is a startup aid, not certification of every ERP module or legal compliance.
